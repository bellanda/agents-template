## Invariantes não negociáveis

- **Componentes**: <200 ideal | 200–350 monitor | 350–500 split | 500+ proibido. Named exports. Typed props. `interface` para shapes, `type` para uniões. Sem `any` — `unknown` + type guard. `@/` absolute imports (NUNCA `../../../`).
- **React 19**: `ref` como prop direto (`forwardRef` LEGADO). `<MyContext value={...}>` direto (`.Provider` LEGADO). Document metadata inline (`<title>`/`<meta>` hoisted, NÃO use `react-helmet`). Form async / data fetch fora de Query / optimistic / `useEffect + fetch` ou `useEffect + setState` → skill `react-19-patterns`.
- **State**: 5 níveis (local/URL/server/UI/outside-react) — skill `frontend` (ref `state-management.md`). TODA API data em TanStack Query (NUNCA duplicar em Context/store). Filtros/pagination em URL (`useSearch`). Context com `value` SEMPRE `useMemo`.
- **Overlays**: Dialog-first (forms, snippets, confirm, detail, picker). **ZERO Sheet lateral no app**; mobile nav/filtro → Dialog ou Drawer (vaul). Overlay que merece F5/link compartilhável (hub de settings, inspector) → **deep-link via search param**; 2+ itens de configuração na sidebar → consolidar num único item que abre o hub (`h-[85vh] lg:max-w-6xl`, nav lateral + busca). Dialog-em-Dialog SÓ no caso hub→ação efêmera. **A saída do overlay tem DOIS contratos que não se misturam**: `ConfirmDialog`/`AlertDialog` (confirmar, excluir, sair) força uma escolha — sem X, sem click-fora, e por isso o par `Cancelar` + ação afirmativa é OBRIGATÓRIO lá; **qualquer outro Dialog/`FormDialog` tem X + click-fora e NÃO leva botão `Cancelar`/`Fechar`/`Voltar` no footer** (`showCloseButton`/`dismissible` já nascem `true`), que carrega só a ação afirmativa. Botão cujo `onClick` só chama `onOpenChange(false)` é a mesma saída oferecida duas vezes: no celular o footer é `flex-col-reverse`, então o botão inútil vira a linha de baixo colada no safe-area e disputa o alvo de toque do Salvar. Fica no footer o que é ação de NEGÓCIO com nome parecido ("Fechar caixa" submit, "Cancelar orçamento" confirm destrutivo, "Voltar" que retrocede step de wizard). **Overlay que contém `<input>`/`<textarea>`/`<select>` NÃO é `DialogContent` cru — é `FormDialog`** (bullet abaixo). **A geometria mora na BASE do `DialogContent`, não no call site**: `max-h-[calc(100dvh-2rem)] w-[calc(100%-2rem)] overflow-y-auto overscroll-contain`. O `-translate-y-1/2` centra pela ALTURA DO CONTEÚDO, então sem `max-h` o dialog alto joga a metade de cima pra fora da tela e nenhum scroll alcança (`position: fixed` + body travado pelo `react-remove-scroll`) — é o "dialog sai pra cima e não dá pra ver o conteúdo". O MESMO `overflow-y-auto` promove `overflow-x` a `auto` (regra do CSS: um eixo não-`visible` promove o outro), então conteúdo largo (imagem sem `max-w-full`, tabela, `<pre>`) rola dentro do dialog em vez de esticar o documento e fazer a página panar pro lado. `w-[calc(100%-2rem)]` e não `w-full`: call site que troca o `max-w` não pode levar junto a margem lateral do mobile. **Abaixo de 768px o call site NÃO manda na geometria** — a base fecha com `max-md:max-h-[calc(100svh-3rem)] max-md:max-w-[calc(100%-2rem)]`: `max-h-[85vh]`/`h-[92vh]`/`max-w-4xl` são medidas de DESKTOP e no iOS `vh` é a viewport GRANDE (ignora as barras do browser), então 85vh ≈ 100% da área visível e o dialog, centrado pela LAYOUT viewport, nasce metade embaixo da barra de cima; `svh` é a viewport pequena e cabe com as barras abertas. Como é VARIANTE, o `tailwind-merge` não funde com a classe crua do call site e o Tailwind emite depois — no celular vence. Full-bleed proposital (lightbox) é opt-in: `max-md:max-h-none max-md:max-w-none`. Skill `frontend` (refs `overlays.md` + `settings-dialog.md`).
- **Campo nativo ≥16px no celular**: todo `<input>`/`<textarea>`/`<select>` de `components/ui/` (`input.tsx`, `textarea.tsx`, o `CommandInput` do `EntityPicker`, qualquer `*Input` próprio) é `text-base … md:text-sm` — mobile-first: a classe sem prefixo é a do celular, o `md:` devolve a densidade do desktop. O gatilho do auto-zoom do iOS é a fonte **computada do próprio campo**, NÃO a do `<html>`: com `html { font-size: 17px }`, `text-sm` = 14.875px e `text-xs` = 12.75px — os dois abaixo do limiar. Zoomado, a visual viewport encolhe e pana, e todo `position: fixed` — o dialog inteiro — some **pra cima e pra esquerda** sem conteúdo visível; é indistinguível de "o dialog quebrou" e só acontece no celular. Campo que HERDA a fonte de um wrapper (`ComboboxChipsInput` dentro de `ComboboxChips text-xs`) precisa da classe no próprio input. PROIBIDO "resolver" com `maximum-scale=1`/`user-scalable=no` (mata pinch-zoom, WCAG 1.4.4) ou com regra global `input { font-size: 16px !important }` (atropela campo intencionalmente maior). Skill `frontend` (ref `mobile-keyboard.md`).

- **Form dialogs & teclado mobile**: TODO dialog com campo editável usa `ui/form-dialog.tsx` (`FormDialog`) — NUNCA `DialogContent` cru. O teclado do iOS **não** encolhe a layout viewport (`vh`/`dvh`/`svh` ficam iguais); ele encolhe e **desloca** a visual viewport, e com o body travado pelo `react-remove-scroll` o `position: fixed` sobe e sai pela borda de cima. Assinatura no DevTools: borda direita do dialog em ~50% da largura do aparelho + altura visível ~50% da tela — não é `vh`, não é teclado, não é zoom. 3 faixas — header `shrink-0` / corpo `min-h-0 flex-1 overflow-y-auto overscroll-contain` / footer `shrink-0` com `padding-bottom: max(env(safe-area-inset-bottom), .75rem)`; **sem o `min-h-0` o footer sai da tela e a solução inteira falha**. `size` de 4 degraus (`sm|md|lg|xl`) — cada degrau **recrava o `sm:`** (`tailwind-merge` não deduplica variantes diferentes, e `lg:max-w-2xl` sozinho perde pro `sm:max-w-*` da base entre 640–1024px). PROIBIDO: `max-h-[Nvh]`/`h-[Nvh]` em dialog de form · `overflow-y-auto` no `className` do `FormDialog` (cria 2º scroller e joga o footer pra fora) · `autoFocus` no primeiro input (são DUAS supressões: `onOpenAutoFocus` do Radix **e** o `autoFocus`, que o React honra por conta própria) · `scrollIntoView` para o campo focado (no iOS rola o documento e realimenta o bug — aritmética manual sobre `scrollTop`) · vaul/Drawer como "solução de teclado" (é Radix Dialog por baixo, mesmo deslocamento). `index.html` com `viewport-fit=cover, interactive-widget=resizes-content` — `viewport-fit` é app-wide e exige as compensações de safe-area no mesmo commit. ## TanStack Router

- Auth em `beforeLoad` ONLY (zero flash). `throw redirect(...)`.
- **`beforeLoad` é SÍNCRONO** — lê `authStore.getState()` e decide. Zero `await`, zero fetch, zero mutação async de store, zero espera por bootstrap (`waitForAuthCheck`/polling com deadline). O bootstrap resolve ANTES do router montar; um guard que espera sessão vira redirect falso quando o deadline estoura primeiro — que é exatamente o caso comum em celular/3G.
- `defaultPreloadStaleTime: 60_000` mínimo (`0` = request storm em hover).
- Stores (`organizationStore`, `authStore`) lidos dentro de `beforeLoad` (fora do React).

## API Layer

- `camelCase` ↔ `snake_case` no `ApiClient` ONLY. Components/hooks sempre `camelCase`.
- `client.get<T>()` → `ApiResponse<T>`: `{ data, status, success }`.
- Lists → `PagedResponse<T>`: `{ items, total, skip, limit, hasMore? }`. `hasMore` é opcional só como dobradiça de migração — fallback `skip + items.length < total`.
- Adapter (baseURL+headers) → ApiClient (fetch+key rename) → Query function (extrai `res.data`) → `useCrud` (paged pattern).
- **`fetch` cru SÓ para API externa** (BrasilAPI, IBGE, ViaCEP). Todo endpoint próprio passa pelo `ApiClient` — inclusive download (`getBlob`) e resposta que precisa do payload sem rename (`getRaw`). Fora do client não existe interceptor de 401: a chamada morre com o access expirado e o usuário só recupera com F5.
- **Falha de rede tem UMA mensagem, em pt-BR** — `lib/api/network-error.ts` (`NETWORK_ERROR_MESSAGE` + `isNetworkError`), aplicada nos **dois** pontos de normalização: `adapters/*.transformError` E `ApiClient.defaultErrorTransform`. Corrigir só um deixa o outro reaparecer no primeiro erro que não passa pelo adapter. Detecção é **`error instanceof TypeError`**, NUNCA `error.message === "Failed to fetch"`: o texto muda por browser ("Load failed" no WebKit/iOS, "NetworkError when attempting to fetch resource" no Firefox), então casar por string manda justo o iPhone pro ramo genérico — o usuário lê "Load failed" em inglês e o erro nem chega como `NETWORK_ERROR`. A mensagem crua do browser vai só em `details.originalError`, nunca na tela.
